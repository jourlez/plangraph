# plangraph 1.0: the final plan

Status: proposal for the owner's approval, written 2026-11-26 after 0.5.0. Replaces the open 0.5.0 gaps in `docs/audit/0.5.0-audit.md` and the remaining items of the amendment.

## Goal

A public 1.0 whose first job is to give Claude Code a small, accurate, always-fresh map of the project (stack, repos, team, tickets, requirements) so it plans and works from that map instead of reading files, and which works beside Jira, GitHub, the superpowers plans and CODEOWNERS instead of replacing them. No human has to run anything for it to be useful, and every answer is token-bounded.

## Ranking criteria (from the owner)

1. The graph and integration with the tools teams already use, never fighting them.
2. Usable by Claude Code automatically, without a human, and cheap in tokens.
3. Better context digestion: a map of tech stack, repos, teams, tickets and requirements.
4. Launch without flaws or gaps (this is a hard gate, not a priority: nothing ships until it passes).

## Principles

- Read from the tool of record, never write to it. The plan graph stores observations (uncommitted, advisory) and its own facts (committed). No account ids, emails, tokens or hosts are ever committed (D24).
- Reuse the user's existing access (the Jira keychain entry that exists, the `gh` CLI session). plangraph never stores a new credential.
- One call answers one question, under a stated token bound, with a count of what was left out and how to ask for it.
- Every feature has a caller. A library function with no command, hook or tool that reaches it does not ship.
- Every new module carries tests of its own behavior and mutation pins for its security-relevant and ordering logic.

## Priorities, in order

### P1. Live, read-only integration (criterion 1)

What exists: the provider seam, `import` from saved files, the observation cache, `sync --plan` drift, a GitHub reader that takes a saved file.

What is missing and must be built:

1. `plangraph sync` fetches, then compares. Jira through the existing `jira-pull` path and keychain entry; GitHub through the `gh` CLI the user already authenticated (pull requests, branches, reviews, CODEOWNERS), no token handled by plangraph. Fetching is bounded (page and byte caps), read-only, and fails to a stale-but-usable cache, never to an error that stops a session.
2. Identity mapping that does not commit identities: a local, uncommitted alias map from tracker identities to plan person ids, with a drift finding `UNMAPPED_ASSIGNEE` instead of a false `DRIFT_ASSIGNEE`. Sprint mapping from tracker sprint id or name to plan sprint number, stored the same way.
3. Drift becomes actionable: each finding names the one command that would reconcile it in the plan (a `whatif`, `sp-link --track`, or a hand edit), and `sync` can print only what changed since the last run.
4. Superpowers plans, Jira, GitHub, CODEOWNERS and `catalog-info.yaml` all land in the same graph with `xrefs` and `touches` edges carrying `conf` and `why`. `touches` is written by a command (`repo link` or inside `sync`), not only computed in a library.
5. A provider contract test pack so a new provider (Linear, Confluence, Asana) is one file plus fixtures.

Acceptance: on a synthetic project with a Jira export and a GitHub export, a single `sync` produces a correct drift report with zero false positives from naming, and nothing committed contains an identity.

### P2. Zero-touch use by Claude Code, token-efficient (criterion 2)

What exists: the SessionStart hook runs `card --if-present --heal`; MCP tools `ready`, `whatif`, `ticket`, `graph`; read-only resource templates.

To build:

1. `plangraph context` (and the MCP tool `context`): one call that returns a digest for the current task. It finds the ticket from the branch name or the open plan task, then returns the ticket, owner, sprint, blockers, the repos it touches with their stack and commands, the people and teams to ask, and the requirements it satisfies. Default bound 400 tokens, `-v` lifts it, truncation is counted.
2. The SessionStart hook injects a short map line plus the `context` digest when a ticket is detected, and refreshes the cache in the background when it is stale. It never blocks start-up and never prints more than its bound.
3. The skills' `allowed-tools` and routing cover every command the graph needs (`graph`, `map`, `context`, `sync`, `import`, `repo`, `graph-materialize`), so Claude can run them without a prompt.
4. A token budget test for every default output, enforced in CI, plus a regression benchmark of tokens per question against reading the raw files.
5. The MCP gaps closed to what clients actually use: `outputSchema` on the graph tools, `concise` and `detailed` modes, `ttlMs` on resources. `server/discover` only if a client needs it; otherwise it is recorded as out of scope.

Acceptance: in a fresh session on the synthetic project, with no human command, Claude answers "what blocks this branch's ticket and which repo and owner does it touch" from the injected digest and one tool call, under the stated token bounds.

### P3. The map: stack, repos, team, tickets, requirements (criterion 3)

What exists: repo nodes from `repo scan` (languages, package manager, runtime, frameworks, commands, entry points, deploy, owners), people, sprints, epics, capacity, ticket and plan links.

To build:

1. `plangraph map`: one overview of the project in a fixed shape (stack by repo, teams and owners, epics with progress, open requirements), under 500 tokens by default, with `pg:` URIs for drill-down.
2. A `team` node (from CODEOWNERS groups and the people file) and a `requirement` node (from superpowers specs, plan headings and optional tracker epics), with links `satisfies` (ticket to requirement), `owned_by`, `part_of`, `depends_on` between repos. This is a schema addition: it needs a format version decision (see Decisions).
3. Tech-stack depth that helps an agent act: test command, lint command, how to run one test, build and deploy commands, ports and env var names (names only, never values), and monorepo package boundaries. Read from manifests and CI files with the existing allowlist and size caps.
4. Staleness: every scanned fact carries `src` and `fp`; `check` reports a map older than the repo state and `scan --check` is wired to the hook so the map refreshes itself.
5. The format benchmark (Task 7B) finished: a runner, a real-model run of the question set, and a written ruling on the default answer form. The result decides the shape of `context` and `map`.

Acceptance: the benchmark shows fewer tokens and equal or better accuracy than the raw-file baseline, with Wilson intervals recorded.

### P4. Make the whatif and verify core trustworthy (supports all three)

1. `verify` enforces `BLOCKED` and `SPRINT_CLOSED`, so whatif and verify cannot disagree; the differential tests extend to those reasons.
2. `whatif` calls the solver for the repair suggestion (Task 15 wired to the CLI), with a time bound and a fallback to `proposeMove`.
3. Solver flags for stage folding and neighborhoods, then the measurement of Task 16 run once and its result recorded.
4. Integrity violations carry line numbers.

### P5. Reach and onboarding

1. `plangraph init` or a first-run skill detects an existing Jira, GitHub, superpowers plans and CODEOWNERS and offers to build the map in one step.
2. Skills and README document every command with a copyable example run on the synthetic plan; every example is a test.
3. A migration story: a 0.3.0 client cannot read node files; ship `doctor` text and a release note that name the exact upgrade order.

## Launch gate (criterion 4)

All of these pass before the 1.0 tag:

1. Every item in the 0.4.0 and 0.5.0 audit "Known gaps" is fixed or removed from the product. No dead exported feature remains (knip plus a caller check).
2. The skipped Task 4 tests, the forward-compatibility fixture, the xref merge limit and the start-up and size measurement are automated and in CI.
3. Mutation pins cover `import`, `provider`, `drift`, `integrity`, `files`, `views`, `repo`, `touches` and `context`; zero surviving non-equivalent mutants in the trust roots.
4. The three flaky tests (`steal race`, `jsonl-read` idle timeout, macOS shard 2 timeout) are made deterministic. The release workflow finishes green from a clean tag, and the 0.5.0 release is re-run or superseded.
5. Hostile-input fuzz covers every command and every file in the graph, and a review for secrets, personal data, home paths and company names passes on the whole tree and its history.
6. Public-launch basics verified: LICENSE, SECURITY.md, CONTRIBUTING, install instructions that work from a clean machine, release artifacts with checksum and attestation, a demo on the synthetic plan.
7. An independent review (a different model or a person) reads the final diff of each priority before merge.

## Order, parallelism and process

| Wave | Work | Runs |
|---|---|---|
| 1 | P4 (verify parity, integrity line numbers); flaky-test fixes; release re-run | parallel, disjoint files |
| 2 | P1 items 1 to 3 (fetch, identity map, actionable drift) | one agent per item after the schema for the alias map is fixed |
| 3 | P3 schema (team, requirement), then `map`; P1 items 4 and 5 | schema first, alone |
| 4 | P2 `context`, hook, skills, MCP gaps | after P1 and P3 data exists |
| 5 | P3 benchmark run and ruling; P4 solver flags and repair wiring | parallel |
| 6 | P5, launch gate, independent review, 1.0 release | alone |

Process: sonnet implementers, one worktree per task, a targeted test run per task (the 0.4.0 and 0.5.0 cycles that ran no tests per task needed a long fix-up tail), the full gate once per wave and at release, a different reviewer per wave. Commits keep the existing rules: plain subjects, no AI attribution, no private data.

## Decisions needed from the owner

1. Is the `team` and `requirement` addition allowed to bump the format version (1.0 is the natural place), or must it stay additive under `x-` types?
2. May `sync` call the `gh` CLI and the existing Jira path on its own at session start, or only on an explicit command?
3. Which tracker comes next after Jira and GitHub for the provider contract (Linear, Confluence, Asana)?
4. Is the public repository the current history, or the `public` branch built from a scrubbed history?

## Out of scope for 1.0

Writing to any tracker, hosting a service, a web UI, credentials management beyond reading what the user already has, and any provider beyond those listed in P1.
