# plangraph 1.0 design: the project graph that Claude Code runs on

Status: proposal for the owner's approval, 2026-11-26. Evidence base: `docs/research/2026-11-26/` (six reports; every decision below names the report section it rests on, and every unverified claim is listed in section 10 with the task that resolves it). Supersedes `docs/superpowers/plans/2026-11-26-final-1.0-plan.md`.

## 1. Purpose

plangraph turns a project, from a single requirements document or from ten years of history, into a small, deterministic, always-fresh graph that Claude Code uses without a human running anything. The graph links requirements, decisions, plans, tickets, people, teams, repos, the tech stack and the history that explains them. It coordinates the work end to end, generates and refreshes the documents that describe the project, and integrates with the tools a team already uses without replacing or fighting them.

Owner priorities, in order: (1) the graph and integration with other tools; (2) automatic use by Claude Code, token-efficient, no human required; (3) better context digestion through a map of stack, repos, team, tickets and requirements. Launching public without flaws or gaps is a hard gate on top of these.

## 2. What the research changes about the obvious design

1. Context files that repeat what the repo already says do not help agents and can raise cost by more than 20 percent (report 01 section 3; report 02 section 4). So the graph stores only facts an agent cannot cheaply discover (owners, decisions, requirement links, plan-to-ticket-to-repo links, history-derived coupling) and answers by tool call, not by a large injection.
2. Evidence that graph structure beats plain retrieval is thin and mixed (report 02 section 4: one benchmark at 99.4 versus 78.2 percent on hidden dependencies, with 58 percent of trials never calling the tool; another at 10x fewer tokens but lower accuracy). So 1.0 ships its own A/B benchmark and does not claim a benefit it has not measured (tasks 4 and 32).
3. Existing code-graph servers model symbols, calls and imports but not owners, teams, systems, requirements or decisions (report 02 section 1). That layer is the open lane; plangraph does not rebuild a symbol graph.
4. Claude Code surfaces MCP resources only through user `@` mentions, so every read path must also be a tool (report 01 section 1). Hook and plain stdout injection is capped at 10,000 characters, with a 2,000 character preview above that.
5. Facts a program can compute must never come from an LLM, and LLM text carries provenance and an input hash (report 03 sections 4 and 6; report 05 section A2).
6. A local plugin cannot receive webhooks, so integration is polling with a `since` cursor, conditional requests and a periodic full reconcile (report 03 section 2; report 04 section 3).
7. Tracker state is reconciled by observe-and-diff with per-field ownership, never by silent two-way writes (report 05 section B6).

## 3. Principles

- Two layers of truth. Committed facts are small, human-meaningful and byte-deterministic: tickets, people, teams, repos, requirements, decisions, links, task events, stored as described in section 4.0. Everything volatile or derived from history or trackers is an uncommitted observation or cache, rebuildable by anyone, git-ignored, mode 0600.
- Read from the system of record, never write to it. plangraph proposes tracker actions as structured data; the agent performs them through the vendor MCP server or the user's own CLI and reports the resulting id back.
- No credential is stored by plangraph. Jira uses the existing keychain entry; GitHub uses the user's `gh` session. Tokens and identities never reach a committed file (D24).
- Every answer is bounded and says what it left out and how to ask for it.
- Every feature has a caller (a command, hook, tool or skill). Dead library code does not ship.
- All text from trackers, pull requests, commits and documents is untrusted data: fenced, length-capped, never inlined as instructions.
- Deterministic first. A generator, parser or linker is code; Claude is used for judgment (decomposition, narrative), and its output is stored with provenance.

## 4. Data model (format 2)

The new files are named format 2 only because the 0.x directories used 1. plangraph has never launched, so 1.0 provides no migration and no compatibility: a pre-1.0 directory is refused with `unsupported pre-1.0 directory: recreate it with plangraph takeover`. All compatibility code for pre-launch versions is removed (task 5).

### 4.0 Storage (decided after research reports 07 to 09 and two independent audits)

The first design kept one sorted JSONL file per entity kind and a custom git merge driver. Research (report 07) found three weaknesses: a merge driver lives in local git config, so GitHub and GitLab web merges, CI merge queues, fresh clones and agent sandboxes get plain text merge on a sorted file; a clean text merge can create duplicate keys or broken order that nothing checks; and one large file per kind gives unreadable review diffs and a hot file every edit touches. The most-used agent tracker (beads) moved to a versioned database at a much larger scale than ours, then restored its file-based classic mode after solo users objected (report 07 section 1). Server databases, binary SQLite, graph servers and CRDT binaries were rejected (reports 07 to 09: they break review in a pull request or need a server, and add no measured benefit at this size). A first version of this section claimed that edits to different fields of one entity "merge cleanly"; an audit reproduced with real git that adjacent fields and concurrent link additions conflict, so the claims below are the corrected ones.

The decision:

1. **One file per entity** under `nodes/<kind>/<h2>/<slug>~<h8>.pg`, where `h8` is the first 8 hex of the sha256 of the exact id, `h2` its first two characters (256 directories, so a 100,000 entity project averages about 400 files per directory), and `slug` the lower-cased, sanitized id (readable and safe on case-insensitive file systems because ids that differ only in case get different hashes). Two branches that edit different entities touch different files, so stock git, the GitHub merge button and CI merge them with no driver. Two branches that create the same id get an add/add conflict, which is the right signal. New ids for locally created entities (requirements, decisions, teams, ad hoc tickets) are short hashes of their creation input, never sequence numbers, so two branches cannot collide. Tracker keys (`ABC-12`) and `sp:<slug>/<n>` keys are natural ids.
2. **A comma-free line format** (`.pg`) instead of JSON: line 1 is `id "<id>"`, then one line per field, `<name> <json value>`, sorted by name; a collection (links, xrefs, acceptance lines, member lists) repeats its name once per element, elements sorted. No commas, braces or indentation, so adding one link changes exactly one line, and a formatter cannot rewrite the files. Honest merge behavior: edits to non-adjacent fields merge, edits to adjacent lines conflict, two links inserted at the same sorted position conflict. Conflicts are explicit, local to one file, and mechanically repairable: `plangraph resolve` unions the collection-field lines of a conflicted file and leaves scalar conflicts for a person, and readers skip a damaged file with a finding instead of failing. Provenance (`src`, `fp`, `derivation`) and, for facts that can stop being true, `valid_to` and `superseded_by` are ordinary fields.
3. **Append-only data as batch files**: task events go to `events/<yyyy-mm>/<actor>.<branch-hash>.<day>.jsonl`, one writer per file, so concurrent branches do not append to one file. Ordering uses a hybrid clock: `at` is the maximum of the wall clock and the latest `at` already read, with a per-file `seq`, so a fast clock cannot outrank events it has seen. Audit outputs (evidence, findings, learnings) go to sealed run files named by content hash. Schedule versions are immutable `schedules/<version>.jsonl` files named by content hash, plus a one-line `schedules/CURRENT` (two branches that both change the current schedule conflict there, on purpose). Compaction of old months runs only in CI on the default branch.
4. **Only plan-relevant tickets are committed nodes.** The whole tracker history (a Jira project may hold tens of thousands of issues) stays in the git-ignored `cache/` as observations. A ticket becomes a committed node when it is scheduled or referenced by a plan, a link, a requirement or an open item. Fields that the tracker owns and that change often (`jira_status`, `jira_updated`) are written only by explicit commands, never by hooks.
5. **SQLite stays a rebuildable, git-ignored index**, built incrementally (per-file size and modification time, then a content hash of only the files that changed; this works in and out of git and sees unstaged edits). Path queries that SQL cannot express efficiently (shortest, critical and depth-limited paths: report 08 measured a depth-carrying recursive query running past 55 seconds where a breadth-first search over an in-memory adjacency took 20 ms at 100,000 nodes and 500,000 edges) run on an in-memory adjacency layer built from the index (about 300 ms to load at that size, kept warm by the MCP server).
6. **No custom merge driver, no `.gitattributes` merge entries, no driver repair in the session hook.** Integrity that git cannot guarantee (ids equal to file names, no dangling links, schema, canonical form, sorted arrays, no case collisions, no conflict markers) is enforced by `plangraph check`, which runs in CI, in the optional pre-commit hook and in `refresh`; `plangraph fmt` rewrites non-canonical files. All writes go through validating commands and a staged transaction (an interrupted multi-file write rolls forward or back on the next call); hand edits are allowed and checked. Revisit Dolt or DoltLite only if real cell-level merge becomes necessary and a Node binding exists.

### 4.1 Core node types

Existing: ticket, person, sprint, epic, plantask, openitem, plan, doc, repo. New committed: `requirement`, `decision`, `team`.

| node | file | key | fields |
|---|---|---|---|
| requirement | `nodes/requirement/` | `id` (`R-<n>` or slug) | `text`, `kind` (ears, gherkin, free), `status` (proposed, accepted, dropped), `source` (repo path plus optional `#anchor`, never a URL), `acceptance` (list of short strings), `priority` |
| decision | `nodes/decision/` | `id` (`D-<n>` or ADR number) | `title`, `status` (proposed, accepted, deprecated, superseded, rejected), `date`, `affects` (repo paths or globs), `source`, `derivation` (extracted, inferred, human) |
| team | `nodes/team/` | `id` | `name`, `members` (person ids), `owns` (repo ids) |

`requirement` implemented and verified status is derived, never stored: a requirement is `implemented` when every ticket that satisfies it is done, and `verified` when each also has `test` or `human` evidence (section 5.3).

### 4.2 Core relations

Existing relations are unchanged. New stored relations (kept in the `links` array of the source entity): `satisfies` (ticket to requirement, class trace), `affects` (decision to repo or path, class info), `supersedes` (decision to decision, class info), `member_of` (person to team, class info). Only classes order, load, slot and gate affect verdicts; the new relations are trace or info, so verdicts stay byte-identical for existing data.

### 4.3 Task events

Task events live in batch files (section 4.0 rule 3), ordered by `(at, seq, actor)`. Fields: `at` (UTC to the second), `task` (ticket key), `to` (state), `by` (person id or `agent`), `evidence` (list of `kind:ref`, kinds `pr`, `commit`, `test`, `human`; refs use the existing `sys` grammar, no URLs), `note`. Current state of a task is derived from its events plus its dependency edges.

### 4.4 Uncommitted observation layer (cache, git-ignored)

The existing `cache/<sys>.jsonl` observations stay. New: `cache/git.jsonl` (per-repo module facts from history: commits, churn window, top authors as person ids, coupled paths, hotspot score, with the window and thresholds recorded), `cache/identities.json` (tracker identity to person id, proposed by fuzzy match and confirmed by the agent; never committed). LLM digests and inferred decisions are not part of 1.0: every committed fact is computed by code or written by a person. New index tables: `module`, `identity`, `source_file` plus tables for the three new committed kinds and `event`, all advisory (the solver ignores them).

### 4.5 Provenance on every derived fact

`src` (the source file or system), `fp` (input fingerprint), `derivation` (derived, extracted, inferred, human), `conf` where a link is a guess. Linking evidence ranks branch name above PR title above commit message above body mention (report 03 section 2).

## 5. Capabilities

### 5.1 Takeover: an existing project into the graph (pillar A)

`plangraph takeover` is a resumable pipeline, run by the `takeover` skill with checkpoints in `cache/takeover.json`. Steps, each deterministic and individually runnable:

1. `doctor`, `integrations`: detect Jira, GitHub, superpowers plans, CODEOWNERS, catalog files.
2. `repo scan --all`: stack facts per repo (manifest, runtime, frameworks, test, lint and build commands, monorepo packages, environment variable names only), teams from CODEOWNERS.
3. `ingest git`: full or blobless history only; a shallow clone is refused. Churn, time-windowed coupling, ownership, hotspots, bus-factor flags, with a rename map from `git log -M`. Cursor is the last indexed SHA, verified with `git merge-base --is-ancestor`; on failure, rebuild.
4. `ingest docs`: ADR, MADR and RFC files become decisions; requirements documents become requirements (EARS and Gherkin parsers); plan files go through `sp-ingest`.
5. `sync`: Jira and GitHub observations with cursors; ticket, branch, PR and commit linking by ranked evidence into `touches` links with `conf` and `why`.
6. `identity map`: propose and record tracker identity to person id.
7. `build`, `check`, `map`, `docs build`, and a gap report listing every unknown explicitly instead of guessing.

### 5.2 Orchestration from one document (pillar B)

A requirements or brief document starts a flow. Claude (through the `flow` skill, using superpowers brainstorming and plan writing) decomposes it; plangraph holds the state.

1. `ingest docs` writes `requirement` rows with acceptance criteria.
2. The plan (superpowers format) is ingested by `sp-ingest`, extended so a plan header or task can name `Assignee`, `Ticket`, `Repo` and `Requirement`, which become a schedule row, a `tracked_by` xref, a `touches` link and a `satisfies` link. Task `Files` lines are matched to `repos.paths` to produce `touches` automatically.
3. `flow next`, `flow brief`, `flow claim`, `flow progress`, `flow done` read and append events. `flow brief KEY` returns the token-bounded brief a subagent needs: task steps, Consumes and Produces interfaces, files, the repo stack and commands, the requirements it satisfies, the decisions that affect its paths, and the owner.
4. `flow actions` emits the tracker operations still missing (create this ticket, transition that one) as JSON for the agent to execute through the vendor MCP server; `link` records the resulting ids as xrefs.
5. `flow status` is the live requirements traceability matrix: requirement to task to ticket to pull request to test to state, with orphans reported as findings.

### 5.3 Task state machine

States: `proposed`, `ready`, `claimed`, `in_progress`, `in_review`, `done`, plus `blocked`, `needs_input`, `failed`, `skipped`, `removed`. `ready` and `blocked` are derived from dependency and gate edges (the one blocker definition in `lib/graph/blockers.ts`); the others are asserted by events. `done` requires evidence. When the observation cache shows the pull request merged to the default branch, evidence is `verified`; otherwise the finding `UNVERIFIED_DONE` is raised. A disagreement between plan and tracker (plan done, tracker open) becomes a drift finding, never an overwrite. Field ownership: the plan owns scope, dependencies and acceptance; the tracker owns assignee, workflow status and comments; the git host owns branch and merge facts.

### 5.4 Generated documents kept live (pillar C)

`plangraph docs build|check|list`. Generators are pure functions of the graph: `roadmap`, `rtm`, `architecture` (arc42 headings with explicit "unknown" markers), `adr-index`, `repo-page`, `onboarding`, `release-notes`, plus the existing `status` report. The live copy is Markdown in `docs/plangraph/`, git-ignored by default, rebuilt automatically by `refresh`; CI commits the shared copy (`docs/generated/`) so tracked files never change from a hook. `docs.commit: true` tracks the live copy instead. Generated text follows a data-class policy: ids, plan-written titles and counts by default; person names, tracker text and history authors only when `docs.include` lists them. Each generated region sits between markers `<!-- plangraph:begin id=<generator> fp=<hex> bh=<hex> v=<n> -->` and `<!-- plangraph:end id=<generator> -->`: `fp` is the hash of the input subgraph plus template version, `bh` the hash of the generated body. `docs check` regenerates and compares (CI drift detection). If the body hash no longer matches the stored `bh` a human edited inside the region: the build refuses that region with `REGION_EDITED` unless `--force`. Text outside markers is never touched. Remote mirrors (Confluence, Notion, Google Docs, Claude Docs, Artifacts) are one-way: `docs export --json` produces the payload and the skill publishes it with suggestion mode where the target has one (Google Docs `writeMode: SUGGEST` is the only verified case) and a version check before write.

### 5.5 Live, automatic freshness (pillar D)

- Layer 1, session: `SessionStart` on `startup|resume|clear|compact` runs `card --if-present --refresh`: the card (at most the existing 250 estimated tokens) plus an incremental refresh bounded to 8 seconds that writes only the index and cache. It re-runs on `compact`, so the digest survives compaction. It never blocks and never prints more than its bound.
- Layer 2, prompt: `UserPromptSubmit` runs `hook prompt`, which reads the prompt and emits at most 200 tokens of factual `additionalContext` only when it contains a ticket key or `pg:` URI that exists in the graph; otherwise nothing.
- Layer 3, git: `plangraph hooks install` sets up tracked git hooks (`post-commit`, `post-merge`, `post-checkout`, `post-rewrite`) that call `refresh --fast` and always exit 0. They are hints, never authoritative.
- Layer 4, CI: a template workflow runs `build`, `check`, `docs check` and a nightly full reconcile. CI is the authoritative rebuild.
- Generated documents are kept live by plangraph: `refresh` (session hook, git hooks, CI) rebuilds every stale region into the git-ignored live copy, so the working tree never turns dirty from a hook. Human edits inside a region are refused, never overwritten (`REGION_EDITED`). The committed copy is produced by CI.
- Everything above is idempotent and tolerates a missing git repo, a missing index, a stale cache and a network failure by doing less, silently.

### 5.5b Using the graph at low token cost (pillar E)

- `plangraph map`: owners and teams, requirement status counts, decisions, epics with progress, top hotspots and freshness; a repo's stack only where it differs from the ecosystem default, because facts an agent can read from the repo itself do not help it (reports 01 and 02). Default bound 500 estimated tokens, drill-down by `pg:` URI.
- `plangraph context [KEY | --branch]`: the digest for the task at hand (section 5.2 brief, without steps), default bound 400 tokens. The ticket is found from the branch name, an open plan task, or the argument.
- MCP (off by default today; bundled and on by default in 1.0 only if the final benchmark, task 32, shows it does not hurt): tools `ready`, `whatif`, `ticket`, `graph`, `map`, `context`, `flow_next`, all read-only with `outputSchema`, `structuredContent`, a compact text copy and `readOnlyHint`; a `concise` or `detailed` mode; `resource_link` for bulk detail; the upfront tool and instruction text stays under 3,500 characters (the client cuts at 4,096). Writes stay on the CLI behind `allowed-tools` for the small set of append-only commands (`flow claim|progress|done`, `identity map`).
- Skills route questions to the graph (descriptions lead with trigger keywords within the 1,536 character window) and pre-approve the read commands; writers outside the append-only set need approval.

## 6. Integrations posture

Coexist, do not compete (report 04 section 2). The graph ingests through REST or GraphQL with the user's own read-only access into the local cache, exposes a few typed bounded tools, and joins everything by `(sys, xid)` xrefs modeled on SCIM `externalId`. Relations use Backstage vocabulary with explicit inverses (`ownedBy`, `dependsOn`, `partOf`). Per-edge provenance follows PROV. OSLC, RDF and A2A are not adopted. Provider contract: one file plus fixtures adds a provider; a contract test pack proves it fences untrusted text, caps size and is read-only. Order: Jira, GitHub, then Confluence pages as a source of requirements and decisions (the owner's stack is Atlassian). Linear is not built in 1.0; a provider contract test pack makes it one file plus fixtures later.

## 7. Security

Untrusted text is fenced and length-capped everywhere it is printed, with injection-payload golden tests across `map`, `context`, `flow brief` and the hook output. Fetchers use read-only scopes, bounded pages and bytes, `Retry-After` and ETag handling, and never log tokens. Cache files are 0600. A committed file never contains a URL, host, email or account id (D24); generated documents are scanned for those before write. Hooks never execute repository-provided commands; configuration cannot run a command (existing rule).

## 8. Verification and launch gate

- Per task: failing test first, targeted run, commit.
- Per wave: the full gate (`bulletproof:check`, `knip`, `mutate`, baseline compare), a different reviewer.
- Release: independent review of the whole diff, a real-install check, fuzz on every new file and command, mutation pins on every trust root (`import`, `provider`, `drift`, `integrity`, `files`, `views`, `repo`, `touches`, `history`, `docs regions`, `flow state`), flaky tests fixed, release workflow green from a clean tag, scrub for secrets, personal data, home paths and company names over tree and history, public-launch basics.
- Measurement: live A/B benchmarks (with and without the graph; tokens, tool calls, correctness against ground truth, Wilson intervals, several models, repeated runs) run early on the 0.5.0 surface to shape the design and again at the end to set the defaults; results are published with the release. The owner approved the spend with no cap.

## 9. Decisions (resolved by the owner, 2026-11-26)

1. No format migration and no compatibility with pre-1.0 versions; plangraph has never launched. Compatibility code is deleted (task 5).
2. `refresh` may run inside the SessionStart hook: yes.
3. Generated documents are regenerated automatically by `refresh`: yes. Two audits showed that hooks rewriting tracked files leave dirty trees and can leak tracker text into public repositories, so the live copy is git-ignored and CI commits the shared copy; `docs.commit: true` flips this.
4. Third integration: Confluence (read pages as requirement and decision sources), then Linear. Chosen by the controller from the owner's Atlassian stack.
5. Public repository: a freshly built history, the perfect version only (task 34).
6. Benchmarks: yes, live, thorough, no spend cap (tasks 4 and 32), including a coding-task arm that tests whether the default injections help or hurt.
